# Changelog

Cambios del SDK y notas de comportamiento del API de FiscalAPI que afectan a quien usa el SDK.

## [Sin publicar]

### Cambios incompatibles (BREAKING)

- Se elimina `Person.capital_regime` (estaba deprecado): el API no tiene régimen de capital, ignoraba el valor y nunca lo devolvía. Quite `capital_regime=...` de los `Person(...)` que construya y toda lectura de `person.capital_regime` (ahora lanza `AttributeError`); envíe la razón social sin régimen de capital en `legal_name`. Pasarlo al constructor no lanza error, pero se descarta sin enviarse.
- `TaxCredential` deja de heredar de `BaseDto`: solo tiene `base64_file`, `file_type` y `password` (opcional en el .cer). Quite `id=...`, `created_at=...` y `updated_at=...` de los `TaxCredential(...)` que construya (se descartan sin enviarse) y toda lectura de esos atributos (ahora lanza `AttributeError`). Un código que trate un `TaxCredential` como `BaseDto` (por ejemplo `isinstance(cred, BaseDto)`) ya no lo reconoce.
- El API deja de devolver `stripeCustomerId` y `subscriptionStatus` en las personas (`/api/v4/people` y la persona de las reglas de descarga): eran datos internos de Stripe. Este SDK nunca los modeló en `Person` (el modelo ya los descartaba), así que el código que usa el modelo no cambia; si su integración los lee de la respuesta JSON cruda, quite esa lectura: el campo ya no llega.

### Modelo `Person`

- Nuevos campos opcionales:
  - `phone_number` (`phoneNumber`): lo aceptan la creación y la actualización de personas.
  - `balances`: saldos por tipo de crédito (`CreditBalance`: `credit_type` y `available`, solo lectura). Solo aparecen los tipos que la persona ha tenido; un tipo ausente tiene saldo 0, y un tipo que el SDK no conoce conserva su número.
  - `is_owner` (`isOwner`): `True` si la persona es el owner de su tenant (solo lectura).
  - `country`: país de residencia fiscal expandido (solo lectura).
  - `valid_to` (`validTo`, `datetime`): fin de vigencia de la persona (solo lectura). La asigna el API; casi siempre es `None` y es informativa (no limita el timbrado ni el acceso al API).
- `password`: requerida al crear; al actualizar, `None` o vacía conserva la contraseña actual. El API nunca la devuelve.
- `user_type_id`: `"C"` (cliente, el valor por omisión al crear) o `"U"` (usuario). `"T"` (tenant) solo llega en respuestas: el API lo rechaza al crear y al actualizar solo lo acepta si la persona ya es `"T"`.

### `TaxCredential`

- `password` deja de ser obligatorio en el modelo: el API solo lo exige en la llave privada (.key, `file_type=1`); en el certificado (.cer) no lo usa.

### `InvoicePayment`

- `currency_code` es `str` (antes `Literal["MXN", "USD", "EUR"]`): acepta cualquier clave del catálogo c_Moneda del SAT (por ejemplo `CAD` o `JPY`), que el API valida (400 en `Complement.Payment.CurrencyCode` si no está en el catálogo, viene en minúsculas o es `XXX`). Antes el modelo rechazaba localmente las monedas distintas de esas tres. El valor por omisión sigue siendo `"MXN"`; el código existente no cambia.

### Claves de catálogo en los modelos

- `ProductTax.tax_id`, `ProductTax.tax_flag_id`, `ProductTax.tax_type_id`, `Person.sat_tax_regime_id`, `Person.sat_cfdi_use_id`, `Person.user_type_id` y `tax_flag_code` de `ItemTax`, `PaidInvoiceTax` y `LocalTax` son `str` (antes `Literal` con las claves del catálogo): el SDK envía el valor tal cual, como los SDK de .NET, Node.js, PHP y Java, y el API lo valida (400 de validación con la falla en el campo; ver las notas de productos, personas y claves de catálogo del timbrado). Antes pydantic rechazaba al construir el modelo (`ValidationError`, sin llamar al API) cualquier otro valor, incluida la cadena vacía `""`, que el API acepta en las personas (la guarda sin valor). El código que ya usaba claves del catálogo no cambia.

### Notas del API (sin cambio de forma en el SDK)

- `Person.tax_password` es la contraseña de la llave privada (.key) que la persona guarda en su perfil; el API no la usa para sellar (al timbrar usa la contraseña de los certificados registrados o la de `tax_credentials`). Solo la reciben con valor la propia persona y el owner del tenant; los demás reciben `None`. Al actualizar, `None` la conserva (el SDK no envía los `None`) y `""` la borra.
- `ValidationFailure.attempted_value`: en un 400 de validación, el valor de un secreto (contraseñas, códigos, tokens, archivos y contraseñas de CSD/FIEL) llega enmascarado como `"[masked: n]"` (`n` es su longitud), o `"[masked]"` si la falla es de un objeto o una lista que lo contiene.
- El API ya no devuelve `twoFactorEnabled` en las personas (este SDK nunca lo modeló).
- `TaxFile.tin` es opcional en `tax_files.create()`: si se omite (`None` o vacío), el API usa el RFC de la persona. Si se envía, debe ser el RFC de la persona (sin distinguir mayúsculas); si no, el API responde 400 con la falla en `Tin` (después de comprobar que puede gestionar los certificados de la persona; si no, 403). El API no guarda el valor enviado: el `tin` del archivo siempre es el RFC de la persona.
- Las personas ya no traen `stripeCustomerId` ni `subscriptionStatus` (datos internos de Stripe). `valid_to` y `committed_balance` son de solo lectura: el API los ignora al crear o actualizar. `committed_balance` es un campo heredado que el API ya no calcula y siempre vale 0; para el saldo use `available_balance`, `available_validation_balance` o `balances`.
- Personas: `people.create()` y `people.update()` con un correo que ya pertenece a otra persona, de esta o de otra cuenta (se compara sin distinguir mayúsculas ni los espacios de los extremos), responden 400 de validación con la falla en `Email` y el mensaje `The email is already registered.` (en el SDK, `succeeded` es `False` y `details` vale `"Email: The email is already registered."`). Antes respondía otro 400 (una falla de Identity o el genérico `A record with the same unique values already exists.`). Al actualizar, el correo actual de la persona no cuenta como repetido. El API guarda el correo sin los espacios de los extremos.
- Personas: `people.update()` y `people.delete()` pueden responder 409 con `details` `The person was modified by another request (for example, a failed sign-in). Reload it and try again.` (en el SDK, `http_status_code` 409 y ese texto en `details`) si otra petición modificó a la persona mientras se procesaba: cuenta cualquier escritura a la persona, por ejemplo un inicio de sesión con su correo (exitoso o fallido) o un cambio en su suscripción. No se guarda nada: vuelva a consultar la persona y repita la llamada. Antes la escritura se guardaba igual y podía deshacer el cambio de la otra petición (el bloqueo de la cuenta por intentos fallidos o la sesión recién iniciada). `PATCH /api/v4/people/{id}`, que este SDK no usa, responde el mismo 409.
- Personas: `people.create()` y `people.update()` validan el correo y la contraseña con las reglas de Identity antes de guardar. Un correo con caracteres fuera de `a-z`, `A-Z`, `0-9` y `-._@+` (por ejemplo `ñ`, una vocal acentuada, un apóstrofo o un espacio intermedio) responde 400 de validación con la falla en `Email`, `errorCode` `InvalidUserName` y el mensaje `The email contains characters that are not allowed: 'ñ'. Allowed characters: abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ0123456789-._@+` (con los caracteres rechazados entre comillas). Una contraseña que no cumple las reglas (al menos 6 caracteres, con una mayúscula `A-Z`, una minúscula `a-z`, un dígito `0-9` y un carácter que no sea letra ni dígito; las letras con acento y la `ñ` no cuentan como mayúsculas ni minúsculas) responde una sola falla en `Password` con el mensaje `Password must be at least 6 characters long and contain at least one uppercase letter (A-Z), one lowercase letter (a-z), one digit (0-9) and one character that is not a letter or a digit. Letters with accents and ñ are not uppercase or lowercase letters for this rule.`, el código del primer requisito que no se cumple en `errorCode` (p. ej. `PasswordTooShort` o `PasswordRequiresUpper`) y `attemptedValue` `null` (en el SDK, `succeeded` es `False` y `details` trae la falla con el campo). Antes, al crear, esos valores llegaban a Identity y la falla traía el código en `propertyName` (`InvalidUserName`, `PasswordRequiresUpper`…) con el texto de Identity (p. ej. `Username '…' is invalid, can only contain letters or digits.`) (en el SDK, `details` empezaba con `InvalidUserName:` y ahora con `Email:`); una contraseña corta como `abc` daba dos fallas (`MinimumLengthValidator` y `PredicateValidator`), y al actualizar el API guardaba un correo con `ñ` o una contraseña como `Ñandú12!` (200). Si aun así `people.create()` falla en otra validación de Identity, la falla trae en `propertyName` el campo del request (`Email` o `Password`) y el código de Identity en `errorCode`.
- Facturas (`invoices.create()`): con una moneda extranjera (`currency_code` distinto de `MXN` y de `XXX`), `exchange_rate` 0 o negativo responde 400 de validación con la falla en `ExchangeRate` y el mensaje `If the currency is different from MXN, you must specify the exchange rate of the day of the transaction.` (en el SDK, `succeeded` es `False` y `details` trae la falla con el campo); antes pasaba la validación del API. Con `MXN` sigue siendo exactamente 1. El complemento de pagos sigue la misma regla en el tipo de cambio del pago (`complement.payment.exchange_rate` frente a `complement.payment.currency_code`): con `MXN`, exactamente 1 (si es `None`, el API usa 1); con otra moneda, mayor que 0. Si no, responde 400 de validación con la falla en `Complement.Payment.ExchangeRate` (mensaje `If the currency is MXN, you must specify the exchange rate equal to 1` o el de moneda extranjera); antes llegaba al PAC, que lo rechazaba, o el pago salía con totales en 0.
- Cambios del API en los endpoints de cuenta, que este SDK no usa (se autentica con API key), así que no le afectan: `POST /api/v4/account/register` y `POST /api/v4/account/info` con un correo que ya pertenece a otra persona responden 400 de validación con la falla en `Email` (`NewEmail` en `info`) y el mensaje `The email is already registered.`; `POST /api/v4/account/change-password` con la contraseña actual incorrecta responde 400 de validación con la falla en `CurrentPassword` (`errorCode` `PasswordMismatch`, mensaje `Incorrect password.`); en general, las fallas que vienen de Identity en `account/change-password`, `account/info`, `account/reset-password` y `account/confirm-email` traen en `propertyName` el campo del request que las causó (`CurrentPassword`, `NewPassword`, `NewEmail`, `ResetCode` o `Code`) y el código de Identity en `errorCode` (`PasswordMismatch`, `InvalidToken`, …), en lugar del código como `propertyName`; `POST /api/v4/account/refresh` con un refresh token vencido responde 401 `Invalid refresh token` en lugar de emitir otro (con uno vigente devuelve el mismo token), así que una sesión iniciada con `account/login` solo se puede renovar hasta 7 días después del login.
- Facturas (`invoices.create()`): con `currency_code` `XXX` (facturas de pago y de traslado), un `exchange_rate` distinto de 1 y de 0 responde 400 de validación con la falla en `ExchangeRate` y el mensaje `If the currency is XXX, the exchange rate does not apply: omit it (or send 1 or 0).` (en el SDK, `succeeded` es `False` y `details` trae la falla con el campo); antes, con un valor mayor que 1 lo rechazaba el PAC (CFDI40116 en un ingreso, CRP20109 en un pago) y con uno entre 0 y 1 o negativo se timbraba ignorándolo. Con 1 (si es `None`, el API usa 1) o 0 se sigue timbrando, sin `TipoCambio` en el XML.
- Facturas de pago (`invoices.create()` con `complement.payment`): la moneda del pago (`complement.payment.currency_code`) y la de cada factura pagada (`currency_code` de cada elemento de `complement.payment.paid_invoices`) se validan contra el catálogo c_Moneda del SAT, escritas tal cual: si se omiten, no están en el catálogo (también en minúsculas, como `mxn`) o son `XXX`, responde 400 de validación con la falla en `Complement.Payment.CurrencyCode` o en `Complement.Payment.PaidInvoices[n].CurrencyCode` (`n` = posición, desde 0) con el mensaje `La moneda '<valor>' no existe en el catálogo c_Moneda del SAT.`, `La moneda de un pago o de un documento pagado no puede ser XXX.` o el de campo vacío (en el SDK, `succeeded` es `False` y `details` trae la falla con el campo); antes llegaban al PAC, que las rechazaba (CFDI40113, CRP20213 o CRP20236). La moneda de la factura de pago (`currency_code`) debe ser `XXX`: con otra, 400 de validación en `CurrencyCode` con `La moneda de un comprobante de pago debe ser XXX.` (antes, el PAC respondía CRP20104). Una factura sin `currency_code` responde una sola falla en `CurrencyCode` (antes, dos).
- Factura global (`invoices.create()` con `global_information.year`): el año acepta el de la fecha de la factura (`date`) y los 5 anteriores, como el SAT (con fecha en 2026, de 2021 a 2026); antes solo el año en curso o el anterior, y por ejemplo 2021 a 2024 respondían 400 aunque el SAT los timbra. Fuera de ese rango responde 400 de validación con la falla en `GlobalInformation.Year` y el mensaje `Year must be the year of the invoice date (2026) or one of the 5 previous years.` (con el año de la fecha) (en el SDK, `succeeded` es `False` y `details` trae la falla con el campo).
- Más cambios del API en los endpoints de cuenta, que este SDK no usa: `POST /api/v4/account/register` (`Email`, `Password`), `POST /api/v4/account/info` (`NewEmail`, `NewPassword`), `POST /api/v4/account/change-password` y `POST /api/v4/account/reset-password` (`NewPassword`) aplican las mismas reglas de correo y contraseña que las personas (400 con `InvalidUserName` o con la falla única de la contraseña); antes `register` creaba la cuenta con un correo con `ñ` o una contraseña como `Ñandú12!`. `reset-password` valida la contraseña nueva antes del código (con las dos inválidas, la falla es la de `NewPassword`). En `account/info`, `CurrentPassword` ya no se valida con las reglas de formato (una incorrecta responde `PasswordMismatch` en `CurrentPassword`) y es obligatoria cuando viene `NewPassword`: sin ella, 400 de validación en `CurrentPassword` con `Current password is required to set a new password.` (antes, el mismo texto en un 400 sin campo).
- Certificados: `tax_files.delete()` hace una baja lógica: el certificado deja de aparecer en todas las consultas y el API deja de usarlo para timbrar; borra el archivo y su contraseña y conserva solo el registro (tipo, RFC, vigencia, quién lo eliminó y cuándo). La respuesta no cambia: 200 con `true`, o 400 con `false` si no existe, ya se había eliminado o es de otra persona. Para volver a usar un certificado eliminado, súbalo de nuevo con `tax_files.create()`. `GET /api/v4/tax-files/load`, que este SDK no usa, devuelve `password` descifrada, como las demás consultas (antes, el texto cifrado).
- Certificados: el servicio de certificados no tiene `update` (`tax_files` nunca lo tuvo en este SDK, así que su forma no cambia): el API retiró `PUT /api/v4/tax-files/{id}`, que ahora responde 405 (Method Not Allowed); antes nunca actualizaba un certificado (respondía un error). Para cambiar un certificado, suba el nuevo con `tax_files.create()` y elimine el anterior con `tax_files.delete()`.
- Facturas (`invoices.create()`): con el RFC genérico (`XAXX010101000` o `XEXX010101000`) el régimen fiscal del receptor debe ser `616` y su código postal el de `expeditionZipCode`; con el régimen `616` el uso CFDI debe ser `S01` o `CP01`; y una factura de ingreso (`I`) a `XAXX010101000` `PUBLICO EN GENERAL` debe traer `globalInformation`. Si no, responde 400 de validación (en el SDK, `succeeded` es `False` y `details` trae la falla con el campo), con todas las fallas juntas, antes de timbrar y sin consumir timbre, en `Recipient.TaxRegimeCode` (`With the generic RFC (XAXX010101000 or XEXX010101000) the recipient tax regime must be 616 (CFDI40159).`), `Recipient.ZipCode` (`With the generic RFC (XAXX010101000 or XEXX010101000) the recipient zip code must be the expedition zip code (CFDI40149).`), `Recipient.CfdiUseCode` (`With the recipient tax regime 616 the CFDI use must be S01 or CP01 (c_UsoCFDI, CFDI40161).`) o `GlobalInformation` (`An income invoice to XAXX010101000 'PUBLICO EN GENERAL' is a global invoice: globalInformation is required (CFDI40130).`). Vale igual con el receptor por valores y por referencia (`recipient.id`: se revisan los datos de la persona guardada). Antes las rechazaba el PAC con un 400 sin campo (CFDI40159, CFDI40149, CFDI40161 y CFDI40130).
- Facturas: la factura que devuelven `invoices.create()` y `invoices.get_by_id()` trae `Invoice.global_information`: completa (`periodicity_code`, `month_code` y `year`) en una factura global, o `None` si no es global o si es una global timbrada antes de este cambio (el XML timbrado conserva la información global). Antes la respuesta no traía el campo (el modelo quedaba en `None`).
- Facturas (`invoices.create()`): el tipo de factura y sus complementos deben corresponder, como exige el SAT: `I` admite `complement.localTaxes`, `complement.cartaPorte` y `complement.comercioExterior` (o ninguno); `E`, `complement.localTaxes` y `complement.comercioExterior` (o ninguno); `T` requiere `complement.cartaPorte` o `complement.comercioExterior`; `P` requiere `complement.payment` y `N`, `complement.payroll`; `T`, `P` y `N` no admiten otro complemento. Si falta el complemento que el tipo requiere, viene uno que no le corresponde (por ejemplo `payroll` en un ingreso, `cartaPorte` en un pago o `localTaxes` en un traslado) o `complement` llega vacío, responde 400 de validación con la falla en `Complement` (en el SDK, `succeeded` es `False` y `details` trae la falla con el campo), antes de timbrar y con el mensaje del tipo: `An invoice of type I (ingreso) must omit complement or send only complement.localTaxes, complement.cartaPorte or complement.comercioExterior.`, `An invoice of type E (egreso) must omit complement or send only complement.localTaxes or complement.comercioExterior.`, `An invoice of type T (traslado) requires complement.cartaPorte or complement.comercioExterior and accepts no other complement.`, `An invoice of type P (pago) requires complement.payment and accepts no other complement.` o `An invoice of type N (nómina) requires complement.payroll and accepts no other complement.` Antes, sin el complemento que el tipo requiere (o con `complement` vacío) respondía un error 500 (`No mapper found for invoice request`); con un complemento que no le correspondía, la factura llegaba al PAC, que la rechazaba (por ejemplo CRP20101 con `payment` fuera de `P` o CP114 con `cartaPorte` en `P` o `E`), o el complemento sobrante se omitía sin aviso (por ejemplo `localTaxes` en un pago), y un `I` con `payroll` se enviaba como nómina (`N`). `POST /api/v4/invoices/calculate`, que este SDK no usa, responde igual, y con un `typeCode` fuera del catálogo responde 400 en `TypeCode` (antes, 500).
- Facturas (`invoices.create()`): el 400 de un `typeCode` fuera del catálogo dice `El tipo de comprobante '<valor>' no existe en el catálogo c_TipoDeComprobante del SAT.` (antes `Please use the SAT catalog values: I,E,T,P,N,P`, con la `P` repetida; ver la nota de claves de catálogo del timbrado).
- Facturas (`invoices.create()`): una fecha ausente, `null`, vacía o que no se reconoce como fecha responde 400 de validación en el campo (en el SDK, `succeeded` es `False` y `details` trae la falla con el campo) en lugar de llegar al PAC como `0001-01-01` (que la rechazaba con CFDI40101 o CFDI40999): `date` → `Date` con `'Date' is missing or is not a valid date in the format yyyy-MM-ddTHH:mm:ss.`; `complement.payment.paymentDate` → `Complement.Payment.PaymentDate` con `'Payment Date' is missing or is not a valid date in the format yyyy-MM-ddTHH:mm:ss.`; y `complement.payroll.paymentDate`, `initialPaymentDate` y `finalPaymentDate` → `Complement.Payroll.PaymentDate`, `Complement.Payroll.InitialPaymentDate` y `Complement.Payroll.FinalPaymentDate` con `'Payment Date'`, `'Initial Payment Date'` o `'Final Payment Date' is missing or is not a valid date in the format yyyy-MM-dd.` Una fecha del año 1 (`0001-01-01…`) cuenta como ausente y responde el mismo 400 en el campo; antes, con la zona horaria de México (`America/Mexico_City`), el API la convertía a otra hora del año 1, no la reconocía como ausente y la factura llegaba al PAC (CFDI40101 o CFDI40999).
- Facturas (`invoices.create()`): una factura `I`, `E` o `T` sin `items` (o con la lista vacía) responde 400 de validación con la falla en `Items` y el mensaje `'Items' must contain at least one item for typeCode I, E and T.` (en el SDK, `succeeded` es `False` y `details` trae la falla con el campo), sin ir al PAC; antes la rechazaba el PAC (CFDI40999 o CP999: el nodo `Conceptos` es obligatorio en el CFDI). En `P` y `N` se siguen omitiendo: el API genera el concepto. `POST /api/v4/invoices/calculate`, que este SDK no usa, aplica la misma regla (antes respondía 400 sin mensaje) y, con un total 0 (todo `T` y `P`, o un ingreso con descuento del 100 %), responde 200 con el cálculo (antes, 400 con `succeeded` `false`).
- Facturas con Carta Porte o Comercio Exterior (`invoices.create()`): el API valida los datos de esos complementos antes de timbrar (obligatorios, longitudes, patrones y catálogos del SAT): una falla responde 400 de validación con la falla en el campo, en `Complement.CartaPorte.…` o `Complement.ComercioExterior.…` (por ejemplo `Complement.CartaPorte.Ubicaciones[0].NumEstacionId` con `NumEstacionId must be a valid c_Estaciones value.`) (en el SDK, `succeeded` es `False` y `details` trae la falla con el campo), sin consumir timbre; antes esas reglas no se aplicaban y el PAC rechazaba la factura (CPxxx, CCExxx o CFDI40101). La fecha de salida o llegada de cada ubicación de Carta Porte sigue la regla de las demás fechas: ausente, vacía, del año 1 o ilegible responde 400 en `Complement.CartaPorte.Ubicaciones[n].FechaHoraSalidaLlegada` con `'Fecha Hora Salida Llegada' is missing or is not a valid date in the format yyyy-MM-ddTHH:mm:ss.` (antes llegaba al PAC como `0001-01-01`). Las claves de estación (c_Estaciones) se escriben como en el catálogo del SAT, con acento cuando lo llevan: `Juárez0` se acepta y `Juarez0` responde 400. El `NumRegIdTrib` del receptor del complemento Comercio Exterior (`complement.comercio_exterior.receptor.num_reg_id_trib`) se ignora, como antes: el API usa el del receptor del CFDI (`recipient.foreign_tin`, o el de la persona receptora por referencias); puede omitirlo.
- Facturas: los errores de lectura del request (un valor de otro tipo, JSON mal formado, cuerpo vacío o un campo obligatorio ausente o `null` dentro de un complemento, por ejemplo `Complement.CartaPorte.TranspInternacId` con `'TranspInternacId' no debe estar vacío.`) responden el mismo 400 de validación que las demás reglas, con la falla en el campo, en lugar de un ProblemDetails (`application/problem+json`): en el SDK, antes `message` era `Error processing server error response` y `details` el cuerpo crudo; ahora `succeeded` es `False`, `message` es `Sorry, it's not me, it's you.` y `details` trae las fallas como `Campo: mensaje` separadas por `; `. En esas fallas `errorCode` es `null`. Un cuerpo que no se puede leer responde una sola falla: un valor de otro tipo, en su ruta (por ejemplo `$.items[0].quantity`), y un JSON mal formado, en `$` (la raíz del JSON), ambos con el texto en inglés del lector de JSON; un cuerpo vacío o `null`, en `$` con `El cuerpo de la petición es requerido y no debe estar vacío.` El ProblemDetails de antes traía además en `errors` la clave del parámetro del endpoint (`command`, `The command field is required.`) y, con un cuerpo vacío, la clave vacía (`""`); ya no llegan. Vale para todos los endpoints.
- Mensajes de validación en español (todos los endpoints): los `errorMessage` generales de las validaciones del API pasan de inglés a español, por ejemplo `'<Campo>' no debe estar vacío.` (antes `'<Campo>' must not be empty.`) o `'Tipo Cambio USD' debe ser mayor que '0'.`, y también los de lectura del request: `'TranspInternacId' no debe estar vacío.` (antes `The TranspInternacId field is required.`), `El cuerpo de la petición es requerido y no debe estar vacío.` (antes `A non-empty request body is required.`) y `El valor 'abc' no es válido para PageNumber.` (antes `The value 'abc' is not valid for PageNumber.`). En el SDK cambia el texto de `details`; `propertyName`, `errorCode`, `message` (`Sorry, it's not me, it's you.`), `details` (`One or more validation failures have occurred.`) y la forma del 400 no cambian. Conservan su texto los mensajes propios de cada regla (varios en inglés, como los citados en estas notas) y los del lector de JSON (JSON mal formado o un valor de otro tipo, en inglés). Si su integración compara el texto del mensaje, use el campo de la falla (`property_name`) en su lugar.
- Certificados, timbrado y cancelación por referencias: `tax_files.get_default_references()`, `tax_files.get_default_values()`, `invoices.create()` con el emisor por referencia (`issuer.id`) y `invoices.cancel()` de una factura emitida por referencias, cuando la persona (o el emisor) solo tiene vigente uno de los dos archivos del CSD, responden 404 con `No se encontró la llave privada de la persona: <id>` o `No se encontró el certificado de la persona: <id>` (en el SDK, `http_status_code` 404 y ese texto en `details`); suba el archivo que falta. Antes, las referencias por defecto y la cancelación respondían un error 500, `get_default_values()` respondía 200 con un solo archivo y el timbrado respondía 400 con `Ambos certificado y clave privada son requeridos para crear un credencial FIEL o CSD.` Sin ningún archivo vigente, las referencias por defecto, el timbrado y la cancelación responden el mismo 404 con `No se encontró tal recurso. Verifica los archivos fiscales de la persona: <id>`; antes, ese 404 solo lo daban las referencias por defecto, el timbrado respondía 400 con `No se proporcionaron archivos fiscales para crear un credencial FIEL o CSD.` y la cancelación 400 en inglés con `When issuer data is missing, issuer's certificates must be configured.` `get_default_values()` sin ningún archivo vigente sigue respondiendo 200 con la lista vacía. En el timbrado, `<id>` es el `issuer.id` enviado; en la cancelación, el id del emisor de la factura.
- Certificados: `tax_files.get_default_references()` aplica la misma regla que `tax_files.get_default_values()`: solo la persona misma o el owner del tenant obtienen las referencias de sus certificados. Si la API key es de una persona que no es el owner y pide las referencias de otra persona, responde 403 con `Solo el propietario de la cuenta puede gestionar las credenciales de otra persona: correo, contraseña, API keys y certificados.` (en el SDK, `http_status_code` 403 y ese texto en `details`); antes respondía 200 con los ids y la vigencia de los certificados de esa persona.
- Reglas de reporte (`/api/v4/reportrules`, que este SDK no usa): `PUT` y `DELETE` sobre la regla predeterminada de FiscalAPI (compartida con todas las cuentas) responden 403 con `Operation denied.` (en el SDK, `http_status_code` 403 y ese texto en `details`); antes el API permitía modificarla o borrarla. `DELETE` de un id que no existe responde 404 (antes, 400 con `false`).
- Facturas por referencias (`invoices.create()` con `issuer.id`, `recipient.id` o `items[n].id`): cuando a la persona o al producto guardado le falta un dato fiscal, el API responde 400 en español con un solo formato, `La persona emisora '<id>' no tiene <dato> (<campo>).`, `La persona receptora '<id>' no tiene <dato> (<campo>).` o `El producto '<id>' no tiene <dato> (<campo>).`, por ejemplo `La persona emisora '<id>' no tiene RFC (tin).` o `La persona receptora '<id>' no tiene uso de CFDI (satCfdiUseId).` (en el SDK, `http_status_code` 400 y ese texto en `details`). En las personas el dato es `RFC (tin)`, `razón social (legalName)`, `régimen fiscal (satTaxRegimeId)` o `código postal (zipCode)`, y en la receptora también `uso de CFDI (satCfdiUseId)`; en el producto, `clave de producto o servicio (satProductCodeId)`, `clave de unidad (satUnitMeasurementId)`, `objeto de impuesto (satTaxObjectId)` o `descripción (description)`. Antes, 400 en inglés sin el id: `Issuer Tin is required`, `Issuer LegalName is required`, `Issuer SatTaxRegimeId is required`, `Issuer ZipCode is required`, `Recipient <Campo> is required` y `Product <Campo> is required`. El código 400 y la forma del error no cambian; un id que no existe sigue respondiendo 404 con `No such resource for the given Id: <id>`.
- Cancelación por referencias (`invoices.cancel()` con `id`): con el id de una factura que no existe o que es de otra cuenta, el API responde 404 con `No such resource for the given Id: <id>` (en el SDK, `http_status_code` 404 y ese texto en `details`); antes respondía un error 500 (`Something went wrong on our end.`). Si la persona emisora de la factura ya no existe (se eliminó), responde 400 con `No se encontró la persona emisora '<id>' de esta factura. Para cancelarla, envía invoiceUuid, tin y taxCredentials (cancelación por valores).` (`<id>` es el id del emisor; antes, 400 en inglés con `When issuer data is missing, issuer's Id must  be provided.`): cancélela por valores con `invoice_uuid`, `tin` y `tax_credentials`. Si la persona emisora no tiene RFC, responde 400 con `La persona emisora '<id>' no tiene RFC (tin).` (antes `La persona '<id>' no tiene datos fiscales`).
- Reglas de descarga (`download_rules.create()`, `download_rules.update()` y `download_rules.delete()`): solo el owner del tenant crea, actualiza o elimina una regla de la persona owner (`person_id` del owner). Con la API key de otra persona del tenant, el API responde 403 con `Solo el propietario de la cuenta puede modificar al propietario de la cuenta.` (en el SDK, `http_status_code` 403 y ese texto en `details`) y la regla no se crea, no cambia ni se elimina; antes el API lo permitía (al crear, respondía 200 o el error de asientos o de FIEL; ahora el 403 llega antes de esas revisiones). Las reglas de las demás personas no cambian.
- Consultas por id: con un id que no existe o que es de otra cuenta, `invoices.get_by_id()`, `invoices.get_xml()`, `invoices.get_pdf()` (`invoice_id`), `invoices.get_status()` (`id`), `people.get_by_id()`, `people.update()`, `people.delete()`, `stamps.get_by_id()`, `products.get_by_id()`, `download_rules.get_by_id()`, `download_rules.delete()`, `download_requests.get_by_id()`, `download_requests.delete()`, `download_requests.download_package()`, `download_requests.download_sat_request()` y `download_requests.download_sat_response()` responden 404 con `No such resource for the given Id: <id>` (en el SDK, `http_status_code` 404 y ese texto en `details`), la misma respuesta que ya daban otras rutas por id (por ejemplo `invoices.send()`); el `message` es `Sorry, it's not me, it's you.` Antes cada una tenía su propio texto: `invoices.get_by_id()`, `Not found such resource: <id>`; `invoices.get_xml()`, `No such resource for the given id: <id>`; `invoices.get_status()`, `stamps.get_by_id()`, `download_rules.delete()`, `download_requests.delete()`, `download_requests.download_sat_request()` y `download_requests.download_sat_response()`, `No such resource for given id: <id>`; `people.get_by_id()` y `people.delete()`, `No such resource for the given id:<id>`; `products.get_by_id()`, `Product with id: <id> not found`; `download_rules.get_by_id()`, `Rule with id: <id> not found`; `download_requests.get_by_id()`, `Sat request with id: <id> not found`; y `download_requests.download_package()`, `No existe una solicitud de descarga con id <id>.` con el `message` `Not Found`. `invoices.get_pdf()` y `people.update()` respondían 400 (con `No such resource for given id: <id>` y `No such resource for the given id: <id>`); ahora, 404. `PATCH /api/v4/people/{id}`, que este SDK no usa, responde igual que `people.update()`. Si su integración reconoce el "no encontrado" por el texto, use el código 404.
- Catálogos (`catalogs.get_record_by_id()`): una clave que no existe en el catálogo responde 404 con `No such resource for the given Id: <id>` (en el SDK, `http_status_code` 404 y ese texto en `details`); antes respondía 400 con `Record not found for <catálogo> with ID <id>` en `message` y `details` vacío. Un nombre de catálogo que no existe responde 404 (ver la nota de nombres de catálogo); las claves que existen responden igual que antes.
- Productos (`products.create()` y `products.update()`): las claves de catálogo del producto y de sus impuestos se validan antes de guardar y responden 400 de validación con la falla en el campo y el mensaje en español (en el SDK, `succeeded` es `False` y `details` trae la falla con el campo): `SatUnitMeasurementId`, `La clave de unidad '<valor>' no existe en el catálogo c_ClaveUnidad del SAT.`; `SatTaxObjectId`, `El objeto de impuesto '<valor>' no existe en el catálogo c_ObjetoImp del SAT.`; `SatProductCodeId` (si se envía, también vacío), `La clave de producto o servicio '<valor>' no existe en el catálogo c_ClaveProdServ del SAT.`; y en cada impuesto (`n` = posición, desde 0), `ProductTaxes[n].TaxId`, `El impuesto '<valor>' no existe en el catálogo c_Impuesto del SAT.`; `ProductTaxes[n].TaxTypeId`, `El tipo factor '<valor>' no existe en el catálogo c_TipoFactor del SAT.`; y `ProductTaxes[n].TaxFlagId`, `La naturaleza del impuesto '<valor>' no es válida: usa T (traslado) o R (retención).` Una clave vacía (salvo `SatProductCodeId`) responde el mensaje de campo vacío. Antes, un `SatProductCodeId` o un impuesto inválido respondía 400 sin campo, con `Sorry, it's not you, it's me.` y `The operation cannot be completed because the record is related to another non-existent record.`, y la clave de unidad y el objeto de impuesto, `Please use the SAT catalog values: <todas las claves del catálogo>`. `SatProductCodeId` en `null` sigue permitido. Una actualización rechazada ya no borra los impuestos guardados del producto (antes, `products.update()` con un impuesto inválido respondía el error y dejaba el producto sin impuestos). En este SDK, `tax_id`, `tax_flag_id` y `tax_type_id` de `ProductTax` son `str` (ver «Claves de catálogo en los modelos»): el SDK envía el valor tal cual y estas fallas las responde el API.
- Personas (`people.create()` y `people.update()`; también `PATCH /api/v4/people/{id}`, que este SDK no usa): el régimen fiscal, el uso de CFDI, el país y el tipo de persona que no son del catálogo responden 400 de validación con la falla en el campo y el mensaje en español (en el SDK, `succeeded` es `False` y `details` trae la falla con el campo): `SatTaxRegimeId`, `El régimen fiscal '<valor>' no existe en el catálogo c_RegimenFiscal del SAT.`; `SatCfdiUseId`, `El uso de CFDI '<valor>' no existe en el catálogo c_UsoCFDI del SAT.`; `CountryId`, `El país '<valor>' no existe en el catálogo c_Pais del SAT.`; y `UserTypeId`, `UserTypeId debe ser uno de: C, U. 'T' está reservado y solo se permite cuando la persona ya es Tenant.` (al actualizar, `T` se sigue aceptando si la persona ya es `T`). Antes, al actualizar, el régimen fiscal y el uso de CFDI respondían `Please use the SAT catalog values: <lista del catálogo>`; al crear, y el país en las dos operaciones, 400 sin campo con `Sorry, it's not you, it's me.` y `The operation cannot be completed because the record is related to another non-existent record.`; y el tipo de persona al crear, `UserTypeId must be one of: C, U`. Los valores vacíos se siguen aceptando (se guardan sin valor). En este SDK, `sat_tax_regime_id`, `sat_cfdi_use_id`, `user_type_id` y `country_id` de `Person` son `str` (ver «Claves de catálogo en los modelos»): el SDK envía el valor tal cual (también `""`; para no enviar valor use `None`) y estas fallas las responde el API.
- Facturas (`invoices.create()`): una moneda que no está en el catálogo c_Moneda (también en minúsculas, como `mxn`) responde 400 de validación en `CurrencyCode` con `La moneda '<valor>' no existe en el catálogo c_Moneda del SAT.` (en el SDK, `succeeded` es `False` y `details` trae la falla con el campo); antes, `Please use the SAT catalog values: <todas las claves de c_Moneda>`. La moneda del pago y la de cada factura pagada usan el mismo texto (ver la nota de facturas de pago).
- Catálogos (`catalogs.get_record_by_id()`, `catalogs.search_catalog()` y `download_catalogs.list_catalog()`): un nombre de catálogo que no existe responde 404 con `No existe el catálogo '<nombre>'.` (en el SDK, `http_status_code` 404 y ese texto en `details`); el `message` es `Sorry, it's not me, it's you.` Antes respondía 400 con `Invalid catalog name: <nombre>` en `message`, o un error 500 con algunos nombres (por ejemplo `Database` o `Users`). El nombre distingue mayúsculas y minúsculas (`satpaymentforms` no es `SatPaymentForms`), como antes; los nombres válidos son los que devuelven `GET /api/v4/catalogs` y `GET /api/v4/download-catalogs`, y responden igual que antes. `GET /api/v4/catalogs/<nombre>` y `GET /api/v4/catalogs/<nombre>/load`, que este SDK no usa, responden el mismo 404 (antes, 400 y 500).
- Productos (`products.create()` y `products.update()`): una descripción (`description`) de más de 255 caracteres responde 400 de validación con la falla en `Description` y el mensaje `'Description' debe ser menor o igual que 255 caracteres. Ingresó <n> caracteres.` (en el SDK, `succeeded` es `False` y `details` trae la falla con el campo). Antes, al crear, respondía 400 sin campo con `Sorry, it's not you, it's me.` y `The operation cannot be completed because the record is related to another non-existent record.`, y al actualizar, 400 con `One or more fields exceed the maximum allowed length.` Con 255 caracteres o menos, sin cambio.
- Claves de catálogo del timbrado (`invoices.create()`) y de los datos de empleado y empleador (`people.employee.create()` y `people.employee.update()`; `people.employer.create()` y `people.employer.update()`): lo que se acepta o rechaza no cambia (mismo 400 y misma falla en el campo), pero el mensaje pasa al español, con el valor y el catálogo y sin la lista de claves (en el SDK, `succeeded` es `False` y `details` trae la falla con el campo): `<El dato> '<valor>' no existe en el catálogo <c_Catálogo> del SAT.` en `TypeCode` (c_TipoDeComprobante), `ExportCode` (c_Exportacion), `PaymentFormCode` (c_FormaPago), `PaymentMethodCode` (c_MetodoPago), el régimen fiscal del emisor, del receptor y a cuenta de terceros (c_RegimenFiscal), el uso de CFDI del receptor (c_UsoCFDI), la unidad (c_ClaveUnidad) y el objeto de impuesto (c_ObjetoImp) de cada concepto, el impuesto (c_Impuesto) y el tipo factor (c_TipoFactor) de los impuestos del concepto y del documento pagado, la periodicidad (c_Periodicidad) y el mes o bimestre (c_Meses) de la información global y el tipo de relación (c_TipoRelacion); en `VersionCode`, `La versión de CFDI '<valor>' no es válida: usa 4.0.`; en la naturaleza (`TaxFlagCode`) de los impuestos del concepto y del documento pagado, `La naturaleza del impuesto '<valor>' no es válida: usa T (traslado) o R (retención).` (en los impuestos locales sigue `The TaxFlagCode must be either 'T' (Traslado) or 'R' (Retención).`); en el código postal de expedición, del receptor y a cuenta de terceros, `El código postal '<valor>' debe tener 5 caracteres (catálogo c_CodigoPostal del SAT).` (en el del receptor también `… debe tener 5 dígitos (catálogo c_CodigoPostal del SAT).` y, si falta, `El código postal es obligatorio.`); en la clave de producto o servicio del concepto y de sus partes, `La clave de producto o servicio '<valor>' debe tener 8 caracteres (catálogo c_ClaveProdServ del SAT).`; en la moneda de una factura de pago (`CurrencyCode`), `La moneda de un comprobante de pago debe ser XXX.`; en los catálogos de Nómina 1.2 (tipo de nómina, percepción, horas extra, otro pago, deducción e incapacidad, y en los datos de empleado y empleador tipo de contrato, régimen, periodicidad de pago, entidad federativa, riesgo de puesto, banco, tipo de jornada y origen del recurso), `La clave '<valor>' no existe en el catálogo <c_Catálogo> del SAT o ya no está vigente.`; y en Sindicalizado, `El valor '<valor>' de Sindicalizado no es válido: usa Sí o No.` Antes, `Please use the SAT catalog values: <lista del catálogo>` (en nómina, `(<catálogo>): <lista>`; a cuenta de terceros, `Utilice los valores del catálogo SAT: <lista>`), `The value does not exist in the SAT catalog <c_X> or is no longer valid.`, `The TaxFlagCode must be either…`, `Please use the SAT 'c_CodigoPostal' catalog values.` o `The currency of an invoice with the payment complement must be XXX.` Cada campo responde una sola falla: en los campos obligatorios con esta regla (por ejemplo `VersionCode`, `TypeCode`, los impuestos o las claves de nómina) un valor vacío o ausente responde solo el mensaje de campo vacío (antes, también el del catálogo), y un `ExpeditionZipCode` inválido, una falla (antes, dos iguales). `POST /api/v4/invoices/calculate`, que este SDK no usa, responde igual. Si su integración compara el texto del mensaje, use el campo de la falla.
